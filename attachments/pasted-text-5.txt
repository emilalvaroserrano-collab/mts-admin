# MTS ADMIN — SARAH CSR AGENT IMPLEMENTATION BLUEPRINT

**Document Version:** 1.0
**Repository:** https://github.com/emilalvaroserrano-collab/mts-admin
**Target Branch:** `main` (development through feature branches and pull requests)
**Priority:** Production-grade agent reliability, user experience, natural conversation
**Scope:** Existing Customer Portal, Sarah Chat, Sarah Voice, Server Functions, Database, Integrations
**Objective:** Implement the agreed Sarah/Miles architecture while preserving existing working features.

---

# 0. PROJECT DIRECTIVE

The developer must upgrade Sarah from a basic chat-and-voice assistant into a context-aware, tool-enabled Customer Service Representative (CSR) capable of interacting with the existing Manage Tech Service application.

**DO NOT build another customer portal. DO NOT replace the existing application framework. DO NOT redesign unrelated modules.**

Improve the existing architecture.

Sarah must:

1. Understand customer intent through natural language.
2. Respond with authentic, native American conversational expressions.
3. Call the correct function tools when actions are required.
4. Display actual backend results within the existing interface.
5. Navigate only when the customer explicitly requests or accepts navigation.
6. Obtain confirmation before financial commitments or material service changes.
7. Continue providing feedback while server operations are running.
8. Preserve user control and avoid blocking the entire application.
9. Reconcile uncertain operations rather than assuming success or failure.
10. Respect customer permissions and backend-authorized fields.
11. Maintain conversational context between related requests.
12. Never claim that an action succeeded without backend verification.

**Core principle:** The application must reflect the actual backend state. Sarah's conversational response must never exceed what the system can prove.

# PHASE 1 — TOOL EXECUTION STATE MACHINE

**Priority: P0 — Must complete before paid-service automation.**

## Task 1.1 — Establish canonical tool states

- [ ] Implement a typed `SarahActionStatus` union.
- [ ] Define the following states:

| State | Meaning |
|---|---|
| `requested` | User intent identified; action created |
| `validating` | Identity, permissions, input, and eligibility being checked |
| `awaiting_confirmation` | Action requires explicit customer consent |
| `executing` | Authorized backend operation is running |
| `checking_status` | Outcome is uncertain; reconciliation required |
| `succeeded` | The intended operation is confirmed by the authoritative system |
| `failed` | Failure has been confirmed; outcome is known |
| `cancelled` | Action was cancelled before execution or cancellation is confirmed |
| `manual_review` | Outcome cannot yet be determined automatically |

- [ ] Keep action status separate from the lifecycle of the underlying resource.
- [ ] A successfully created service request must not be described as an activated service.
- [ ] A successfully created order must not be described as paid.
- [ ] An accepted ticket must not automatically be described as assigned to a technician.
- [ ] Prevent invalid state transitions through a backend state-machine validator.
- [ ] Make each transition auditable.

## Task 1.2 — Build the action state machine

Required state flow:

`requested → validating → executing → succeeded`

For operations requiring approval:

`requested → validating → awaiting_confirmation → executing → succeeded`

For uncertain network outcomes:

`executing → checking_status → succeeded / failed / manual_review`

For declined confirmations:

`awaiting_confirmation → cancelled`

A failed operation is only marked `failed` when the backend can establish that it did not complete, or when a definitive failure has been returned.

A network timeout alone is not proof of failure.

## Task 1.3 — State-specific conversational output

- [ ] Give Sarah access to the current action state.
- [ ] Generate short customer-friendly messages.
- [ ] Avoid technical state names in spoken responses.
- [ ] Keep status messages consistent with the backend.

Examples:

| Backend State | Natural Sarah Expression |
|---|---|
| Requested | "Sure, let me check that." |
| Validating | "Okay, let me pull up your account." |
| Awaiting confirmation | "That'll add eighteen dollars a month. Want me to go ahead?" |
| Executing | "Got it. I'm sending that through." |
| Checking status | "I'm still checking whether that went through." |
| Succeeded | "Done. Your request is in. Here's the reference." |
| Failed | "That didn't go through. I can help you try again." |
| Manual review | "I can't confirm the result yet, so I'm flagging it for the team to check." |

No fabricated progress percentages, fake completion indicators, or arbitrary success messages.

**Acceptance criteria**

- Every agent tool operation has a verifiable state.
- State transitions are validated on the server.
- UI and voice reflect the same state.
- Reconnecting the browser does not reset an in-progress operation.
- Timeout never automatically becomes failure.

# PHASE 3 — IDPOTENCY AND TIMEOUT RECOVERY

**Priority: P0**

## Task 3.1 — Implement idempotency

- [ ] Generate a unique idempotency key for each distinct customer-approved mutation.
- [ ] Associate the key with the authenticated customer and operation.
- [ ] Enforce uniqueness in the database.
- [ ] Return the original result for repeated submissions using the same key.
- [ ] Reject conflicting parameter changes under an existing key.
- [ ] Persist the action record before executing external side effects.
- [ ] Use transactional persistence where supported.
- [ ] Use an outbox/worker model where database writes and external API calls must be coordinated.

Do not assume local database transactions can roll back completed external API operations.

## Task 3.2 — Implement timeout reconciliation

When a request times out:

- [ ] Set `checking_status`.
- [ ] Retain the original action ID and idempotency key.
- [ ] Query local persistent records.
- [ ] If an external provider supports lookup by operation reference, query that provider.
- [ ] Reconcile authoritative results.
- [ ] If a matching completed action exists, show its original receipt.
- [ ] If definitely rejected, report the verified failure.
- [ ] If still unknown, keep checking with bounded retries and eventually escalate to manual review.
- [ ] Never automatically create a second order while the original outcome remains unknown.

## Task 3.3 — Prevent duplicate side effects

Apply duplicate prevention to:

- Service orders
- Equipment orders
- VoIP extensions
- Wiring requests
- Ticket creation
- Published ticket replies
- Payment processing
- Cart additions initiated by Sarah

A new customer request may create a new action. Replaying an existing submission must not.

## Task 3.4 — Handle partial success

Example: service request saved successfully, but Zendesk ticket creation times out.

- [ ] Preserve the successfully created service request.
- [ ] Store the incomplete downstream step.
- [ ] Retry only the missing downstream work using a deduplication key.
- [ ] Do not create a second service request.
- [ ] Show the distinction between local acceptance and external synchronization.
- [ ] Reconcile eventually or flag for human review.

**Acceptance criteria**

- Repeated clicks do not create duplicate orders.
- Refreshing during execution preserves the operation.
- Closing and reopening the portal returns the known state.
- A lost HTTP response cannot accidentally trigger duplicate billing or provisioning.
- External webhook replays do not duplicate effects.

| Provider outage | Report uncertainty and follow recovery policy |
| Partial completion | Resume missing downstream work only |
| Unexpected navigation | Preserve draft and request approval |
| TTS error | Keep text result visible; use safe audio fallback |
| STT error | Offer retry or typed input |

Do not display internal stack traces or secrets to customers.
